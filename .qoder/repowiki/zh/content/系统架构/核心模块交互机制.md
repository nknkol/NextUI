## 项目结构

NextUI项目采用分层架构，主要分为应用层、系统服务层和基础库层。应用层以`nextui`为核心，负责用户界面的渲染与交互。系统服务层包含`batmon`、`wifimanager`、`gametimectl`和`btdaemon`等独立运行的守护进程，提供系统级功能。基础库层（`libcommon`）为上层提供通用的API和工具函数。

## 全局状态管理

### 全局状态结构体

NextUI通过`globals.h`头文件定义了一系列全局变量，实现了跨模块的数据共享。这些变量主要分为三类：UI状态、系统状态和导航状态。

```c
// --- UI 状态全局变量 ---
extern Directory* top;           // 当前目录
extern Array* stack;            // 目录栈
extern Array* recents;          // 最近使用列表
extern Array* quick;            // 快捷菜单项
extern Array* quickActions;     // 快捷操作项

// --- 系统状态全局变量 ---
extern int quit;                // 退出标志
extern int simple_mode;         // 简化模式标志

// --- 导航/恢复状态全局变量 ---
extern int restore_depth;       // 恢复深度
extern int restore_relative;    // 恢复相对位置
extern int restore_selected;    // 恢复选中项
```

### 底层实现

`PLAT_getBatteryStatusFine`函数直接读取Linux系统的`sysfs`虚拟文件系统来获取电池信息。这是一种简单高效的同步I/O操作。

```c
void PLAT_getBatteryStatusFine(int *is_charging, int *charge) {
    *is_charging = getInt("/sys/class/power_supply/axp2202-usb/online");
    *charge = getInt("/sys/class/power_supply/axp2202-battery/capacity");
}
```

此函数被`PWR_updateBatteryStatus`调用，后者由`PWR_update`在主循环中定期执行（默认每5秒一次）。当检测到充电状态或电量变化时，会设置`dirty`标志，触发UI重绘，从而更新界面上的电池图标。

## 与游戏时间跟踪服务的交互

### 同步进程间通信

NextUI通过`system()`函数调用`gametimectl.elf`可执行文件，与游戏时间跟踪服务进行同步交互。这是一种基于命令行的简单IPC（进程间通信）机制。

gametimectl-->>nextui : 命令执行完毕

### 代码实现

在`launcher.c`文件中，当用户选择一个游戏时，`openRom`函数会先调用`system()`启动`gametimectl`服务，然后再启动游戏模拟器。

```c
void openRom(char* path, char* last) {
    // ... 其他逻辑 ...
    char act[256];
    sprintf(act, "gametimectl.elf start '%s'", escapeSingleQuotes(sd_path));
    system(act); // 同步调用，等待命令执行完毕
    // ... 启动游戏 ...
}
```

`gametimectl`服务接收到`start`命令后，会调用`play_activity_start`函数，该函数最终将游戏启动记录写入SQLite数据库。这种设计的优点是简单直接，但缺点是`system()`调用是阻塞的，如果`gametimectl`执行缓慢，会延迟游戏的启动。

## 与WiFi管理服务的交互

### 服务接口

WiFi管理服务通过`libwifimg`库提供C语言API。`wifimanager.c`文件定义了一个`aw_wifi_interface`结构体，其中包含了连接、断开、扫描等操作的函数指针。

```

**节源**
- [wifimanager.c](file://workspace/lib/libwifimg/wifimanager.c#L1591-L1640)

### 交互方式

与`batmon`和`gametimectl`不同，NextUI主应用似乎没有直接调用`wifimanager`的API。相反，它通过`PLAT_isOnline()`等`libcommon`提供的抽象接口来间接获取网络状态。

```c
int is_online = PLAT_isOnline();
if (was_online!=is_online) dirty = 1;
```

这表明WiFi管理服务的交互可能发生在更底层，或者由其他独立的UI组件（如`Settings.pak`中的WiFi设置）来处理。主应用`nextui`只关心最终的网络连接状态，而不直接参与连接过程。

### 交互机制

`btdaemon`通过调用`SetBluetooth()`函数来更新系统的蓝牙状态。该函数定义在`msettings.h`中，用于持久化存储蓝牙连接状态。

```c
void SetBluetooth(int value); // 0-1
int GetBluetooth(void);
```

`nextui`主应用通过`PLAT_bluetoothConnected()`函数来查询蓝牙连接状态：

```c
bool PLAT_bluetoothConnected()
{
    FILE *fp;
    char buffer[256];
    bool connected = false;

    fp = popen("hcitool con", "r");
    if (fp == NULL) {
        perror("Failed to run hcitool");
        return false;
    }

    while (fgets(buffer, sizeof(buffer), fp) != NULL) {
        if (strstr(buffer, "ACL")) {
            connected = true;
            break;
        }
    }

    pclose(fp);
    return connected;
}
```

此函数通过执行`hcitool con`命令来检查当前的蓝牙连接，并将结果返回给调用者。`nextui`主循环会定期调用此函数来更新UI上的蓝牙状态指示器。

### 紧耦合设计的优缺点

**优点**:
1. **简单性**: 全局变量和`system()`调用的实现非常直观，易于理解和维护。
2. **性能**: 直接读取`sysfs`文件和使用全局内存共享，避免了复杂的IPC开销。
3. **事件驱动**: 新增的`btdaemon`采用DBus事件监听，实现了高效的异步通知机制。

**缺点**:
1. **可维护性差**: 全局状态使得模块间的依赖关系不清晰，容易产生难以追踪的bug。
2. **可测试性低**: 由于强依赖于全局状态和外部进程，单元测试变得非常困难。
3. **扩展性差**: 添加新功能或修改现有功能时，容易影响到其他不相关的模块。
4. **进程间依赖**: `btdaemon`与`nextui`通过文件系统和共享库进行通信，增加了系统复杂性。

### 解耦优化方案

1. **引入事件总线**: 使用发布-订阅模式替代全局变量。当电池状态变化时，`PWR`模块发布一个`BatteryStatusChangedEvent`，UI模块订阅该事件并更新视图。
2. **使用异步IPC**: 用命名管道（FIFO）或Unix域套接字替代`system()`调用，实现非阻塞的异步通信。
3. **依赖注入**: 将`PWR`、`WIFI`等服务作为接口注入到需要它们的模块中，而不是通过全局变量访问。
4. **标准化通信协议**: 为`btdaemon`等守护进程定义统一的IPC接口，减少对特定文件和命令的依赖。
