## 系统启动流程

NextUI系统的启动流程始于设备引导阶段，通过一系列shell脚本和系统服务的协同工作，最终初始化主用户界面应用。该流程确保了系统在不同硬件平台上的稳定启动和配置加载。

启动过程从`runtrimui.sh`脚本开始，该脚本首先等待SD卡挂载完成，以确保关键系统文件的可访问性。脚本通过轮询`/proc/mounts`文件来检测SD卡挂载状态，最多等待3秒（6次0.5秒的间隔）。此设计保证了系统在存储设备准备就绪后才继续执行，避免了因文件系统未就绪导致的启动失败。

## 核心架构与设计模式

NextUI系统采用分层架构与事件驱动模式相结合的设计，实现了高内聚、低耦合的软件结构。系统核心由主应用`nextui`、系统服务和平台抽象层三大部分构成，各层之间通过明确定义的接口进行通信。

### 分层架构

系统遵循清晰的分层原则：
1.  **用户界面层 (UI Layer)**: 由`nextui`主应用实现，负责所有用户交互、视觉呈现和导航逻辑。
2.  **服务层 (Service Layer)**: 包含`batmon`、`wifimanager`等独立运行的守护进程，提供电池状态、网络连接等系统级服务。
3.  **平台抽象层 (Platform Abstraction Layer)**: 由`libcommon`库中的`platform.h`和`platform.c`实现，屏蔽底层硬件差异，为上层提供统一的API。

### 事件驱动模型

系统广泛采用事件驱动架构，以响应用户输入和系统状态变化。主应用`nextui.c`中的主循环是这一模式的核心体现。循环通过`PAD_poll()`函数持续轮询输入设备状态，并根据按键事件（如`BTN_A`、`BTN_B`、方向键）改变当前屏幕状态（`currentScreen`）和UI元素的选中状态。

```c
while (!quit) {
    GFX_startFrame();
    PAD_poll();
    
    if (PAD_justPressed(BTN_MENU)) {
        currentScreen = SCREEN_QUICKMENU;
        dirty = 1;
    }
    else if (currentScreen == SCREEN_QUICKMENU && PAD_justReleased(BTN_A)) {
        Entry_open(screen, &dirty, selectedQuickEntry);
    }
    // ... 其他事件处理逻辑
    GFX_sync_fixed_rate(60.0);
}
```

这种设计将控制流从传统的顺序执行转变为基于事件的响应式模型，极大地提高了系统的响应性和可维护性。每个事件处理器只关注特定的输入或状态变化，使得代码逻辑清晰且易于扩展。

## 全局状态管理

NextUI系统通过`globals.h`头文件定义了一套全局状态变量，作为主应用内部以及主应用与部分功能模块间共享数据的核心机制。这些全局变量避免了复杂的参数传递，实现了跨函数和跨模块的状态同步。

### 全局状态分类

根据其用途，全局状态可分为以下几类：

**UI状态全局变量**
- `top`: 指向当前顶层目录的指针，是文件浏览器导航的核心。
- `stack`: 存储目录导航历史的栈，支持用户返回上一级。
- `recents`: 存储最近游玩游戏的数组，用于快速切换。
- `quick` 和 `quickActions`: 分别存储快速菜单和快捷操作项的数组。

**系统状态全局变量**
- `quit`: 布尔标志，当设置为1时，主循环将退出，结束应用。
- `simple_mode`: 布尔标志，指示系统是否运行在简化模式。

**启动/恢复状态全局变量**
- `can_resume` 和 `should_resume`: 控制游戏是否可以以及是否应该从暂停状态恢复。
- `slot_path` 和 `preview_path`: 存储游戏存档和预览图的文件路径。
- `recent_alias`: 指向最近游戏别名的字符串指针。

**导航/恢复状态全局变量**
- `restore_depth`, `restore_relative`, `restore_selected` 等: 用于在应用重启后恢复到之前的UI状态。

### 数据结构与内存管理

全局状态依赖于`datastructures.h`中定义的通用数据结构。`Array`结构体是其中最核心的，它是一个动态数组，用于存储任意类型的指针。其设计包含`count`（当前元素数量）、`capacity`（分配的容量）和`items`（指向指针数组的指针）。

```c
typedef struct Array {
    int count;
    int capacity;
    void** items;
} Array;
```

当向数组中添加元素时，`Array_push`函数会检查容量。如果容量不足，则将容量翻倍并使用`realloc`重新分配内存，确保了添加操作的摊还时间复杂度为O(1)。这种设计在保证灵活性的同时，也兼顾了性能。

## 平台抽象层

平台抽象层（Platform Abstraction Layer, PAL）是NextUI实现硬件无关性的关键技术。它通过`platform.h`头文件定义接口，并在`platform.c`中提供具体实现，将上层应用逻辑与底层硬件细节（如不同型号的TrimUI设备）完全解耦。

### 硬件差异处理

`platform.h`中的宏定义是处理硬件差异的主要手段。最典型的例子是`is_brick`变量和基于它的条件编译宏。系统通过检查环境变量或硬件标识来确定当前运行的设备型号（如"Trimui Brick"或"Trimui Smart Pro"），并据此调整UI布局和硬件参数。

```c
#define MAIN_ROW_COUNT (is_brick ? 5 : 10)
#define FIXED_WIDTH		(is_brick?1024:1280)
#define FIXED_HEIGHT	(is_brick?768:720)
```

上述代码表明，在"Brick"型号上，主列表每页显示5行，屏幕分辨率为1024x768；而在其他型号上则为10行和1280x720。这种设计使得同一套UI代码可以无缝适配不同屏幕尺寸和DPI的设备。

### 统一API接口

`api.h`头文件定义了上层应用与平台层交互的统一接口。例如，`PLAT_getBatteryStatus`函数为上层提供了获取电池状态的标准化方法，而无需关心底层是通过读取哪个sysfs文件或使用何种通信协议来获取数据。

```c
void PLAT_getBatteryStatus(int* is_charging, int* charge);
```

在`platform.c`的实现中，该函数会调用底层硬件相关的函数来读取电池信息，并对原始数据进行处理（如将精确的百分比值离散化为10、20、40...100的档位），然后返回给调用者。这不仅简化了上层逻辑，还提供了数据标准化和错误处理的能力。

### 输入映射与功能绑定

根据最新的代码提交，`platform.h`文件中的输入映射得到了更新，特别是L3、R3、plus和minus按钮的定义。这些按钮不仅在游戏手柄上作为功能键，还被系统用于特定的UI操作。

```c
// 在 platform.h 中定义的按钮代码
#define CODE_PLUS		128
#define CODE_MINUS		129
#define JOY_L3			(is_brick?6:JOY_NA) //（6=实际作为SELECT）
#define JOY_R3			(is_brick?7:JOY_NA) //（7=实际作为START）

// 在 platform.h 中定义的功能绑定
#define BTN_MOD_BRIGHTNESS 	BTN_L3 //亮度控制实际按键
#define BTN_MOD_COLORTEMP 	BTN_R3 //色温控制实际按键
#define BTN_MOD_PLUS 		BTN_PLUS
#define BTN_MOD_MINUS 		BTN_MINUS
```

这些宏定义将物理按钮（如`BTN_L3`）映射到系统功能（如`BTN_MOD_BRIGHTNESS`）。在`defines.h`中，这些功能被进一步定义为位标志：

```c
// 在 defines.h 中定义的按钮ID和位标志
enum {
    // ... 其他ID
    BTN_ID_L3,
    BTN_ID_R3,
    BTN_ID_PLUS,
    BTN_ID_MINUS,
    // ... 其他ID
};

enum {
    // ... 其他位标志
    BTN_L3			= 1 << BTN_ID_L3,
    BTN_R3			= 1 << BTN_ID_R3,
    BTN_PLUS		= 1 << BTN_ID_PLUS,
    BTN_MINUS		= 1 << BTN_ID_MINUS,
    // ... 其他位标志
};
```

这种分层的映射机制（物理按钮 -> 功能 -> 位标志）使得系统可以灵活地为不同设备重新配置输入，同时保持上层应用逻辑的稳定。例如，`PAD_tappedMenu`函数可以检测`BTN_PLUS`或`BTN_MINUS`的短按，而无需关心这些按钮在物理上是如何连接的。

## 系统服务与事件驱动

NextUI系统通过独立的系统服务（System Services）来管理后台任务和硬件资源，这些服务与主应用`nextui`通过进程间通信（IPC）或共享状态进行交互，构成了系统的事件驱动骨架。

### 电池监控服务 (batmon)

`batmon.c`实现了一个后台守护进程，负责监控电池状态并记录使用日志。该服务使用`sqlite3`数据库持久化存储电池活动数据，包括充电状态、电量百分比和持续时间。服务通过信号处理（`SIGINT`, `SIGTERM`）来优雅地处理关闭请求，并在退出时清理临时文件。

服务的核心逻辑是周期性地（每15秒）检查电池状态。当检测到状态变化（如开始充电、停止充电）时，它会向数据库插入一条新记录。为了防止数据库无限增长，服务实现了先进后出（FILO）的清理策略，当记录条数超过1000条时，自动删除最旧的记录。

数据库的交互通过`libbatmondb`库进行封装。`batmondb.h`定义了`open_battery_log_db`和`close_battery_log_db`等接口，而`batmondb.c`则实现了具体的数据库操作，如创建表和执行SQL语句。

### WiFi管理服务 (wifimanager)

`wifimanager.c`是系统网络功能的核心。它通过`wpa_supplicant`守护进程与WiFi硬件交互，并提供了一个事件驱动的API。服务内部维护了一个状态机（`wmgState`），其状态包括`DISCONNECTED`、`CONNECTING`、`CONNECTED`和`OBTAINING_IP`等。

服务的关键机制是事件回调。当WiFi状态发生变化时（例如连接成功或密码错误），`wifimanager`会通过`call_state_callback_function`通知所有注册的监听者。主应用`nextui`可以注册一个回调函数，以便在WiFi连接状态改变时更新UI（如显示信号强度图标）。

### 蓝牙管理服务 (btdaemon)

根据最新的代码变更，系统已添加了完整的蓝牙管理基础设施，由`platform.c`中的平台抽象层API和`btdaemon`守护进程共同实现。

**平台抽象层API**:
`platform.c`文件中定义了一系列`PLAT_bluetooth*`函数，为上层应用提供统一的蓝牙管理接口：
- `PLAT_bluetoothInit()`: 初始化蓝牙管理器，设置回调函数，并启动蓝牙服务。
- `PLAT_bluetoothEnable(bool)`: 启用或禁用蓝牙，通过`rfkill`命令和`bt_init.sh`脚本控制硬件。
- `PLAT_bluetoothDiscovery(int)`: 开始或停止蓝牙设备发现。
- `PLAT_bluetoothScan()`: 扫描并返回已发现的蓝牙音频设备和控制器。
- `PLAT_bluetoothPair()` / `PLAT_bluetoothUnpair()`: 管理设备配对。
- `PLAT_bluetoothConnect()` / `PLAT_bluetoothDisconnect()`: 建立或断开与配对设备的连接。

**蓝牙守护进程 (bt_daemon)**:
`bt_daemon.cpp`是一个C++编写的守护进程，通过D-Bus监听`org.bluez`服务的`PropertiesChanged`信号。当检测到A2DP音频设备连接或断开时，它会自动更新`/mnt/SDCARD/.userdata/tg5040/.asoundrc`文件，将音频输出重定向到蓝牙设备，并通过`SetBluetooth(1)`更新系统设置。

```c
void handleDeviceConnected(DBusConnection* conn, const std::string& path) {
    std::string mac = pathToMac(path);
    if (hasUUID(conn, path, UUID_A2DP)) {
        log("Audio device connected: " + mac);
        writeAudioFile(mac);
        SetBluetooth(1);
    }
}
```

该守护进程与`msettings.h`中的`SetBluetooth()`函数集成，确保系统状态与蓝牙连接状态保持同步。

## 性能优化策略

NextUI系统实施了多项性能优化策略，以确保在资源受限的嵌入式设备上提供流畅的用户体验，其中最关键的是对屏幕撕裂（Screen Tearing）的处理和资源管理。

### 减少屏幕撕裂

屏幕撕裂是由于GPU渲染帧的速度与屏幕刷新率不同步导致的视觉伪影。NextUI通过严格的垂直同步（VSync）策略来消除这一问题。

在`nextui.c`的主循环末尾，调用了`GFX_sync_fixed_rate(60.0)`函数。该函数的目标是将渲染帧率锁定在60.235 FPS（由`SCREEN_FPS`宏定义），与设备的原生屏幕刷新率保持一致。

```c
void GFX_sync_fixed_rate(SDL_Surface* screen, double target_fps) {
    double frame_budget_ms = 1000.0 / target_fps;
    uint32_t frame_duration = SDL_GetTicks() - frame_start;
    if (frame_duration < FRAME_BUDGET) {
        PLAT_vsync(FRAME_BUDGET - frame_duration);
    }
}
```

`PLAT_vsync`函数会调用底层平台的VSync API，强制CPU/GPU等待下一个垂直消隐期（Vertical Blank Interval）的到来，然后再进行帧缓冲区的交换（Flip）。这确保了每一帧都在屏幕刷新的间隙被完整地显示，从而彻底消除了撕裂现象。

### 资源管理

系统通过多种方式优化资源使用：
1.  **延迟加载**: 使用`initImageLoaderPool`函数启动一个独立的线程池来异步加载图像资源（如背景图、缩略图），避免阻塞主UI线程。
2.  **内存池**: 对于频繁创建和销毁的小对象（如UI元素），系统可能使用内存池来减少`malloc`/`free`的开销。
3.  **条件渲染**: `dirty`标志位用于标记UI是否需要重绘。只有当`dirty`为1时，系统才会执行完整的渲染流程，否则会跳过不必要的绘制操作，节省CPU和GPU资源。

## 终端插件与libtsm集成

根据最新的代码变更，系统已集成一个基于`libtsm`库的真实终端后端，为用户提供了一个功能完整的命令行环境。该功能通过`workspace/plugins/terminal/terminal.c`文件中的`Terminal`插件实现。

### 终端会话管理

`Terminal`插件实现了多会话管理，最多支持5个并发会话（`MAX_SESSIONS`）。每个会话由`TerminalSession`结构体表示，包含会话ID、名称、进程ID（`pid`）、主从伪终端文件描述符（`ptm_fd`）以及`libtsm`库的核心对象`tsm_screen`和`tsm_vte`。

会话的生命周期由`create_session`和`delete_session`函数管理。创建会话时，插件通过`fork()`和`openpty()`系统调用创建一个新的进程和伪终端对。子进程执行`/bin/sh` shell，而父进程则通过主终端文件描述符（`ptm_fd`）与之通信。

### libtsm集成与渲染

`libtsm`（Linux Terminal Screen Manager）库被用于处理终端的屏幕管理和虚拟终端仿真。插件通过`tsm_screen_new`和`tsm_vte_new`函数初始化`libtsm`对象，并设置回调函数：
- `draw_cb`: 当`libtsm`需要绘制字符时调用，负责将字符渲染到SDL表面。
- `vte_write_cb`: 当虚拟终端需要向伪终端写入数据时调用，负责将数据通过`ptm_fd`发送给shell进程。

渲染过程在`render_terminal_view`函数中执行，它调用`tsm_screen_draw`，后者会触发`draw_cb`回调，将终端屏幕内容逐字符绘制到主屏幕上。

### 输入处理

插件实现了两种输入模式：通过虚拟键盘（OSK）和直接按键。虚拟键盘由`render_osk`函数渲染，并通过方向键和A键进行选择。当用户在虚拟键盘上按下A键时，对应的字符会通过`write(s->ptm_fd, &ch, 1)`发送给shell进程。此外，插件还直接将`BTN_START`（回车）、`BTN_SELECT`（Tab）和`BTN_X`（退格）等按键映射为相应的控制字符。

### 插件生命周期

`Terminal`插件遵循标准的插件生命周期：
- `plugin_init`: 初始化SDL表面、加载等宽字体（`mono.ttf`）、创建第一个会话。
- `plugin_run`: 主循环，处理用户输入、读取伪终端输出并触发`libtsm`的输入处理（`tsm_vte_input`）。
- `plugin_quit`: 清理所有会话资源，终止子进程，释放`libtsm`对象和字体资源。

该集成通过`makefile`构建系统自动编译和链接`libtsm`库，确保了终端功能的稳定性和可移植性。
